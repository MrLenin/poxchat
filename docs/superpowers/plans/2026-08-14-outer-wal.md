# Outer-DB WAL Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Switch the zstd VFS's *outer* container database to WAL journaling, and make every rename/copy/delete of an outer DB treat `db` + `db-wal` as one unit.

**Architecture:** The VFS is a "database inside a database" (`src/common/sqlite-zstd-vfs.c`): the inner scrollback DB's pages are stored compressed in an outer plain-SQLite file. The inner DB stays on `journal_mode=MEMORY`; only the outer DB's journal mode changes from DELETE to WAL. Spec: `docs/design/2026-08-12-outer-wal-design.md` — read it before starting.

**Tech Stack:** C (C11, GLib, SQLite), PowerShell test suite (`tools/run-vfs-tests.ps1`), standalone C harness (`tools/zstd-vfs-test.c`), Python salvage tool (`tools/scrollback-salvage.py`).

## Global Constraints

- **Pragma order is load-bearing:** `locking_mode=EXCLUSIVE` must execute *before* `journal_mode=WAL` so SQLite uses a heap wal-index and never creates a `-shm` file. Never reorder.
- **Sidecar unit rule:** `db`, `db-wal`, `db-shm` are one unit in every rename/copy/delete. A `-wal` stranded at a path gets replayed into the *next* database created there (corrupting it); a backup/copy without its `-wal` silently loses the un-checkpointed tail. `-shm` is reconstructible cache: delete, never move/copy.
- **Code style:** tabs for indentation; match the surrounding file's conventions (both C files declare variables at block top — keep doing that even though C11 allows otherwise). GLib allocators (`g_strdup_printf`/`g_free`).
- **Harness build:** `pwsh tools\build-vfs-test.ps1` (needs VS 2022 + `c:\gtk-build\gtk4\x64\release`). Suite: `pwsh tools\run-vfs-tests.ps1`. Run from repo root. The suite's `-ExpectKillFail` mode is documentation-only (pre-fix behavior); every new assertion must be guarded with `if (-not $ExpectKillFail)` or placed inside an existing such block.
- **Full app build** (64-bit MSBuild host is mandatory — the 32-bit host OOMs with C1060):
  `& 'C:\Program Files\Microsoft Visual Studio\2022\Enterprise\MSBuild\Current\Bin\amd64\MSBuild.exe' win32\poxchat.sln /p:Configuration=Release /p:Platform=x64 /p:PreferredToolArchitecture=x64 /v:minimal /nologo`
  Known-unrelated failures to ignore: jansson.lib (libenchant_win8/notifications-winrt/perl), lua.h, python cffi, fe-text `fe_get_str`. `LNK1104` on poxchat.exe means the app is running — not a code error.
- **In-place conversion:** `journal_mode=WAL` persists in the outer DB header, so live DBs convert on first open after this change; rollback is reverting the pragma (or a one-off `PRAGMA journal_mode=DELETE` sweep). No migration code is needed or wanted.
- **Commit messages:** repo style is `area: summary` (e.g. `common:`, `tools:`). End every commit message with the `Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>` trailer.
- **Watch-point (do not paper over):** the busy leg (`hold` + `check` expecting exit 2) exercises cross-process locking, which WAL changes. If it stops returning 2 after the flip, that is a real semantic question — stop and investigate with superpowers:systematic-debugging; do not adjust the expected exit code to match observed behavior.

Replace that region with:

```c
static int
outer_db_init (zstd_vfs_file *f, const char *path, int flags)
{
	int rc;
	char *errmsg = NULL;
	char *wal_path;

	f->outer_path = g_strdup (path);

	/* A -wal sidecar at open means the previous session did not close
	 * cleanly (a clean close checkpoints and removes it); SQLite replays
	 * it below.  Log it so unclean exits stay diagnosable. */
	wal_path = g_strdup_printf ("%s-wal", path);
	if (g_file_test (wal_path, G_FILE_TEST_EXISTS))
		g_message ("zstd-vfs: WAL sidecar present at open (unclean previous exit), replaying: %s", path);
	g_free (wal_path);

	/* Open outer DB using the real (OS) VFS — avoids recursion */
	rc = sqlite3_open_v2 (path, &f->outer_db,
	                       SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE, NULL);
	if (rc != SQLITE_OK)
		return rc;

	/* Outer DB pragmas.  Order matters: locking_mode=EXCLUSIVE must be in
	 * effect before the first WAL-mode access so SQLite uses a heap
	 * wal-index and never needs a -shm file (single-process access is our
	 * model; see docs/design/2026-08-12-outer-wal-design.md). */
	sqlite3_exec (f->outer_db, "PRAGMA locking_mode=EXCLUSIVE;", NULL, NULL, NULL);
	{
		sqlite3_stmt *st;
		if (sqlite3_prepare_v2 (f->outer_db, "PRAGMA journal_mode=WAL;", -1, &st, NULL) == SQLITE_OK)
		{
			if (sqlite3_step (st) == SQLITE_ROW)
			{
				const char *mode = (const char *) sqlite3_column_text (st, 0);
				if (!mode || g_ascii_strcasecmp (mode, "wal") != 0)
					g_warning ("zstd-vfs: outer DB refused WAL, running journal_mode=%s: %s",
					           mode ? mode : "(null)", path);
			}
			sqlite3_finalize (st);
		}
	}
	sqlite3_exec (f->outer_db, "PRAGMA synchronous=NORMAL;", NULL, NULL, NULL);
```

Everything after (schema creation etc.) stays unchanged. Do NOT add a `wal_autocheckpoint` pragma — the default (1000 pages) is the deliberate choice per the spec.

- [ ] **Step 4b: Virtualize sidecar visibility in the VFS** *(added after implementation surfaced a same-path collision — see the design doc's §1b)*

The inner logical DB and the outer container share one on-disk path, so the outer's live `-wal` sits exactly where the inner pager's unconditional hot-WAL/hot-journal probe looks. Without filtering, the inner core finds the outer's `-wal`, judges it stale, and tries to delete it while the outer holds it open under an exclusive lock — `SQLITE_IOERR_DELETE` on Windows, failing the first write (100% reproducible at `fill 1`).

In `src/common/sqlite-zstd-vfs.c`:

(a) Add above `zvfs_open`:

```c
/* The inner logical DB shares its on-disk path with the outer container.
 * Sidecar files at that path (-wal/-journal/-shm) therefore belong to the
 * OUTER connection, never to the inner pager: the inner is pinned to
 * journal_mode=MEMORY and must not detect, open, or delete sidecars that
 * are really the outer's (its unconditional hot-WAL/hot-journal probes
 * would otherwise fight the outer's live, exclusively-locked WAL). */
static int
is_sidecar_name (const char *zName)
{
	return g_str_has_suffix (zName, "-wal")
	    || g_str_has_suffix (zName, "-journal")
	    || g_str_has_suffix (zName, "-shm");
}
```

(b) In `zvfs_open`'s else-branch (currently "Passthrough for journal, temp, WAL, etc."), refuse inner main-journal/WAL opens. The `memset` must run BEFORE the guard's `return`: SQLite's xOpen contract requires `sqlite3_file.pMethods` to be valid-or-NULL even when xOpen fails, and the zeroing is what guarantees that (the file's other two error paths already follow this pattern):

```c
		{

		}
```

(c) Replace `zvfs_delete` and `zvfs_access`:

```c
static int
zvfs_delete (sqlite3_vfs *vfs, const char *zName, int syncDir)
{
	zstd_vfs *zvfs = (zstd_vfs *)vfs;

	/* e.g. the inner's journal_mode=MEMORY transition deletes
	 * "<db>-journal" unconditionally; under WAL such names are the outer's
	 * live sidecars.  Report success without touching disk — there is
	 * never an inner sidecar to delete. */
	if (zName && is_sidecar_name (zName))
		return SQLITE_OK;
	return zvfs->real_vfs->xDelete (zvfs->real_vfs, zName, syncDir);
}

static int
zvfs_access (sqlite3_vfs *vfs, const char *zName, int flags, int *pResOut)
{
	zstd_vfs *zvfs = (zstd_vfs *)vfs;

	/* Hide outer-DB sidecars from the inner pager's hot-WAL/hot-journal
	 * probes: to the inner logical database these files do not exist. */
	if (zName && is_sidecar_name (zName))
	{
		*pResOut = 0;
		return SQLITE_OK;
	}
	return zvfs->real_vfs->xAccess (zvfs->real_vfs, zName, flags, pResOut);
}
```

(b) `src/common/sqlite-zstd-vfs.c` — add `#include <glib/gstdio.h>` after the existing `#include <glib.h>`, and add near `zstd_vfs_register`/`zstd_vfs_shutdown` (the public API section at the bottom):

```c
int
zstd_vfs_backup_db (const char *path, const char *backup_path)
{
	char *wal_path, *shm_path;
	int ret = 0;

	if (g_rename (path, backup_path) != 0)
		return -1;

	wal_path = g_strdup_printf ("%s-wal", path);
	if (g_file_test (wal_path, G_FILE_TEST_EXISTS))
	{
		char *wal_backup = g_strdup_printf ("%s-wal", backup_path);
		if (g_rename (wal_path, wal_backup) != 0)
		{
			/* Losing the un-checkpointed tail is recoverable; letting the
			 * next DB created at this path replay a stale WAL is not. */
			g_warning ("zstd-vfs: could not move %s with its database (%s); deleting it",
			           wal_path, g_strerror (errno));
			if (g_unlink (wal_path) != 0)
			{
				/* Neither move nor delete worked: the stale WAL is
				 * stranded where SQLite would replay it into whatever
				 * database is created at this path next.  Undo the main
				 * rename so the pair at least stays together, and report
				 * failure — the caller must not create a DB here. */
				g_warning ("zstd-vfs: -wal stranded at %s (%s); backing out backup rename",
				           wal_path, g_strerror (errno));
				g_rename (backup_path, path);
				ret = -1;
			}
		}
		g_free (wal_backup);
	}
	g_free (wal_path);

	if (ret == 0)
	{
		shm_path = g_strdup_printf ("%s-shm", path);
		if (g_file_test (shm_path, G_FILE_TEST_EXISTS))
			g_unlink (shm_path);
		g_free (shm_path);
	}

	return ret;
}
```

```python
def copy_with_sidecars(src, dst):
    """Copy src plus any -journal/-wal sidecars to dst (+ matching names).
    A -journal holds the rollback of a torn commit; a -wal holds committed
    pages the main file may lack.  -shm is skipped: it is reconstructible
    cache and never valid for a different path.  Returns the list of
    sidecar suffixes copied."""
    shutil.copy2(src, dst)
    copied = []
    for suffix in ("-journal", "-wal"):
        if os.path.exists(src + suffix):
            shutil.copy2(src + suffix, dst + suffix)
            copied.append(suffix)
    return copied
```
